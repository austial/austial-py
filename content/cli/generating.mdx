# Generating Resources

Every schematic writes into `src/app/modules/<snake_case_name>/` (`src/modules/` in projects with the older flat
layout), following the
same one-folder-per-feature convention the rest of the framework uses (see
[Modules](/overview/modules)). Pieces that several modules use go to `src/shared/` instead:
see [Shared code](#shared-code).

## `module` / `controller` / `service`

The three bare schematics are intentionally minimal — a starting point, not
a full feature:

```bash
austial generate module cats
```
```python
# src/app/modules/cats/cats_module.py
@Module()
class CatsModule:
    pass
```

```bash
austial generate controller cats
```
```python
# src/app/modules/cats/cats_controller.py
@Controller("cats")
class CatsController:
    @Get()
    async def find_all(self):
        return []
```

```bash
austial generate service cats
```
```python
# src/app/modules/cats/cats_service.py
@Injectable()
class CatsService:
    pass
```

Running `module` for a name also patches the nearest `app_module.py`,
inserting both the import line and the class into the `imports=[...]`
array — see [App module patching](#app-module-patching) below.

## Guards, pipes, interceptors, filters, middleware, decorators, gateways and more

One file each, with a working skeleton:

```bash
austial generate guard auth            # src/app/modules/auth/auth_guard.py          -> class AuthGuard(CanActivate)
austial generate pipe slugify          # src/app/modules/slugify/slugify_pipe.py     -> class SlugifyPipe(PipeTransform)
austial generate interceptor timing    # .../timing_interceptor.py               -> class TimingInterceptor(NestInterceptor)
austial generate filter database       # .../database_filter.py                  -> class DatabaseFilter(ExceptionFilter), @Catch(HttpException)
austial generate middleware audit      # .../audit_middleware.py                 -> class AuditMiddleware(NestMiddleware)
austial generate decorator roles       # .../roles_decorator.py                  -> def Roles(*values), plus ROLES_KEY
austial generate gateway chat         # .../chat_gateway.py                    -> @WebSocketGateway("/chat") with a message handler
austial generate resolver cats         # .../cats_resolver.py                    -> a Strawberry Query type
austial generate command seed-db       # .../seed_db_command.py                  -> @Command class (austial.commander)
austial generate listener order        # .../order_listener.py                   -> @OnEvent("order.created") handler
austial generate class money           # .../money.py                            -> class Money
austial generate provider mailer       # same as `service`
```

A name may carry a path, which becomes the folder structure under `src/app/modules/`:

```bash
austial generate guard auth/api-key
# src/app/modules/auth/api_key/api_key_guard.py       (every folder gets an __init__.py)

austial generate guard auth/api-key --flat
# src/app/modules/auth/api_key_guard.py               (no folder for the file itself)
```

These schematics create only the file; they don't register anything in a module. Reference the class where you use
it (`@UseGuards(AuthGuard)`, `providers=[...]`, `{"provide": APP_GUARD, "useClass": AuthGuard}`). Existing files are
never overwritten.

## Shared code

Add `--shared` to put a cross-cutting piece in `src/shared/` instead of a feature folder. The file is always flat, in a folder named
after its kind:

```bash
austial generate guard roles --shared        # src/shared/guards/roles_guard.py
austial generate pipe slugify --shared       # src/shared/pipes/slugify_pipe.py
austial generate interceptor timing --shared # src/shared/interceptors/timing_interceptor.py
austial generate filter domain --shared      # src/shared/filters/domain_filter.py
austial generate middleware request-id --shared    # src/shared/middleware/request_id_middleware.py
austial generate decorator roles --shared    # src/shared/decorators/roles_decorator.py
austial generate service mailer --shared     # src/shared/services/mailer_service.py
```

A name may carry a path, which becomes a subfolder (`austial g pipe auth/slug --shared` writes `src/shared/pipes/auth/slug_pipe.py`).
Every folder gets an `__init__.py`. `--shared` applies to `guard`, `pipe`, `interceptor`, `filter`, `middleware`, `decorator`, `service`
and `provider`, and cannot be combined with `--flat`. Like the other component schematics it only creates the file: register a shared
service in a module's `providers` and `exports` yourself.

## Libraries and extra applications

For a repository with more than one deployable (a monorepo), generate shared code and extra apps next to `src/`:

```bash
austial generate library billing        # libs/billing/billing_module.py + billing_service.py (exports BillingService)
austial generate app admin              # apps/admin/app_module.py + main.py
```

```python
# anywhere that should use the library
from libs.billing.billing_module import BillingModule

# run the extra app
austial start --app apps.admin.main:app --watch        # or: uvicorn apps.admin.main:app
```

Both live at the project root, which `austial` and pytest already have on the import path. Libraries aren't registered anywhere
automatically: add `BillingModule` to the `imports` of the apps that use it.

## `resource` — full CRUD

```bash
austial generate resource cats
```

generates a complete feature module:

```
src/app/modules/cats/
├── __init__.py
├── cats_module.py
├── cats_controller.py
├── cats_service.py
├── entities/cats_entity.py
└── dto/
    ├── create_cats_dto.py
    └── update_cats_dto.py
```

`entities/cats_entity.py` — an `@Entity()`-decorated domain entity (see
[Database](/techniques/database) for the full `austial.orm` API):

```python
from austial.orm import Column, Entity, PrimaryGeneratedColumn


@Entity()
class Cat:
    id: int = PrimaryGeneratedColumn()
    name: str = Column()
```

`dto/create_cats_dto.py` / `dto/update_cats_dto.py`:

```python
class CreateCatDto(BaseModel):
    name: str


class UpdateCatDto(BaseModel):
    name: str | None = None
```

`cats_service.py` — CRUD methods backed by an injected `Repository` (this
resolves as soon as an `OrmModule.for_root(...)` is configured somewhere in
the app — see [Database](/techniques/database)):

```python
@Injectable()
class CatService:
    def __init__(self, repository: Repository[Cat] = InjectRepository(Cat)):
        self.repository = repository

    async def create(self, dto: CreateCatDto) -> Cat:
        return await self.repository.save(Cat(**dto.model_dump()))

    async def find_all(self) -> list[Cat]:
        return await self.repository.find()

    async def find_one(self, id: int) -> Cat:
        item = await self.repository.find_one_by({"id": id})
        if item is None:
            raise NotFoundException(f"Cat #{id} not found")
        return item

    async def update(self, id: int, dto: UpdateCatDto) -> Cat:
        await self.find_one(id)
        await self.repository.update(id, dto.model_dump(exclude_unset=True))
        return await self.find_one(id)

    async def remove(self, id: int) -> None:
        await self.find_one(id)
        await self.repository.delete(id)
```

`cats_controller.py` — full CRUD routes, wired to the service above:

```python
@Controller("cats")
class CatController:
    def __init__(self, service: CatService):
        self.service = service

    @Post()
    async def create(self, dto: CreateCatDto = Body()) -> Cat:
        return await self.service.create(dto)

    @Get()
    async def find_all(self) -> list[Cat]:
        return await self.service.find_all()

    @Get(":id")
    async def find_one(self, id: int) -> Cat:
        return await self.service.find_one(id)

    @Patch(":id")
    async def update(self, id: int, dto: UpdateCatDto = Body()) -> Cat:
        return await self.service.update(id, dto)

    @Delete(":id")
    async def remove(self, id: int) -> dict:
        await self.service.remove(id)
        return {"deleted": True}
```

`cats_module.py` — registers the entity with `OrmModule.for_feature(...)`
so `InjectRepository(Cat)` above has something to resolve:

```python
@Module(
    imports=[OrmModule.for_feature([Cat])],
    controllers=[CatController],
    providers=[CatService],
)
class CatModule:
    pass
```

<div style={{ opacity: 0.8, fontSize: "0.9em" }}>
Note: the generator uses the name you type directly for class naming
(via `to_pascal_case`) — it doesn't singularize/pluralize automatically.
`austial generate resource cats` produces `CatController`/`CatService`/`Cat`
because that's what a straightforward pascal-case of "cats" minus its
trailing `s` looks like in the generator's naming convention; check the
generated names before committing.
</div>

## App module patching

`module` and `resource` both call the same text-based patcher
(`register_module`) against your project's `src/app/app_module.py`:

1. Inserts `from src.app.modules.cats.cats_module import CatModule` into the
   existing same-package import block, re-sorted alphabetically.
2. Appends `CatModule` into the `imports=[...]` array literal on the
   `@Module(...)` decorator.

It's idempotent — running the same generator twice, or against an
already-imported module, is a no-op rather than a duplicate entry. If your
`app_module.py` has been hand-edited into a shape the patcher can't
recognize (no clear `imports=[...]` array to append to), it leaves the file
untouched rather than guessing — add the import/array entry by hand in
that case.

## File-already-exists guard

Every generator refuses to overwrite an existing file by default — it
skips and reports it — delete or rename the existing file first if you
intend to regenerate it.

## Previewing with `--dry-run`

Every schematic accepts `--dry-run` (`-d`): it prints the files it *would* create and writes nothing, and for
`module` and `resource` it also leaves `app_module.py` untouched.

```bash
austial generate resource cats --dry-run
```
