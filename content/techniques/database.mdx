# Database

`austial.orm` is a from-scratch, [TypeORM](https://typeorm.io)-shaped ORM: `@Entity()`/`@Column()`
decorators, all four relation types, a `Repository`/`EntityManager` data-mapper API, a fluent
`QueryBuilder`, and transactions — wired natively into Austial's DI container via `OrmModule`,
the same way `@nestjs/typeorm` wires up `typeorm` in Nest.

SQLAlchemy Core is used internally, purely as a hidden SQL-compilation/connection-pooling layer
behind a pluggable `Driver` interface (PostgreSQL via `asyncpg`, SQLite via `aiosqlite` today) —
you never import or see SQLAlchemy anywhere in application code.

## Defining an entity

```python
from austial.orm import Column, Entity, PrimaryGeneratedColumn


@Entity()
class Cat:
    id: int = PrimaryGeneratedColumn()
    name: str = Column()
    age: int = Column(nullable=True)
```

Python has no field-level decorators, so (exactly like `Inject()` elsewhere in Austial) each
column/relation marker is used as the attribute's *default value* — `@Entity()` reads these
markers back off the class, converts it into a real `@dataclass`, and registers its schema
metadata. `Cat` instances are just plain mutable objects (`Cat(name="Tom")`, attribute
access/assignment) — no active-record magic, no lazy proxies, no dirty-checking.

## Setup

```python
from austial import Module
from austial.orm import OrmModule

from src.entities.cat import Cat


@Module(
    imports=[
        OrmModule.for_root(
            type_="postgres",
            url="postgresql+asyncpg://user:pass@localhost/mydb",
            entities=[Cat],
        ),
    ],
)
class AppModule:
    pass
```

Zero-config local development/tests with SQLite:

```python
OrmModule.for_root(type_="sqlite", url="sqlite+aiosqlite:///./austial.db", entities=[Cat])
```

Connection options resolved at runtime from other providers (the common case — reading a URL out
of `ConfigService`):

```python
from austial.config import ConfigService
from austial.orm import OrmModule


OrmModule.for_root_async(
    use_factory=lambda config: {
        "type_": "postgres",
        "url": config.get("DATABASE_URL"),
    },
    inject=[ConfigService],
    entities=[Cat],
)
```

`use_factory` is called with each of `inject`'s tokens resolved and passed positionally, and must
return a dict shaped like `for_root()`'s keyword arguments (`type_`, `url`, any extra
driver-specific kwargs). `entities`/`synchronize` stay static — they describe your app's schema,
not runtime connection config, so they're passed directly to `for_root_async()` itself rather
than through the factory.

### Connecting and closing

`OrmModule` connects the `DataSource` when the application initialises (`app.listen()`, uvicorn's lifespan startup, or
`await app.init()` in tests) and closes it on shutdown, as `TypeOrmModule` does. There is nothing to call yourself, and
repositories can be injected anywhere, including into providers with `on_module_init` hooks. `DataSource.initialize()` is
idempotent, so older code that calls `await app.get(DataSource).initialize()` keeps working.

```python
app = AustialFactory.create(AppModule)      # python src/main.py, uvicorn src.main:app and `austial start` all work
```

`synchronize=True` (dev/test only, not the production path once migrations exist) makes the connection also issue `CREATE TABLE`
for every entity in `entities=[...]`.

Routes are built during startup, after the application initialises, so a controller whose dependencies can't be resolved (a
resource generated without `OrmModule.for_root(...)`, say) fails the startup with the error instead of answering `500` to every
request.

## Repositories

Register entities with `OrmModule.for_feature([...])` in whichever feature module owns them, then
inject a `Repository` with `@InjectRepository()`:

```python
from austial import Injectable
from austial.orm import InjectRepository, Repository

from src.entities.cat import Cat


@Injectable()
class CatsService:
    def __init__(self, repository: Repository[Cat] = InjectRepository(Cat)):
        self.repository = repository

    async def create(self, name: str) -> Cat:
        return await self.repository.save(Cat(name=name))

    async def find_all(self) -> list[Cat]:
        return await self.repository.find()

    async def find_one(self, id: int) -> Cat | None:
        return await self.repository.find_one_by({"id": id})
```

`InjectRepository(Cat)` is typed `Any` (the marker `Container` actually resolves at DI time is an
implementation detail), so it type-checks as the default for a parameter annotated
`Repository[Cat]` — the same trick every other param-marker helper (`Body()`, `Inject()`, ...)
uses.

```python
@Module(
    imports=[OrmModule.for_feature([Cat])],
    providers=[CatsService],
)
class CatsModule:
    pass
```

`Repository[T]` methods: `find(options)`, `find_one(options)`, `find_by(criteria)`,
`find_one_by(criteria)`, `count(options)`, `save(entity | [entities])` (INSERT when the primary
key is unset, else a full-column UPDATE), `insert(entity | [entities])` (always an INSERT — see
below), `remove(entity | [entities])`, `update(criteria,
partial)` and `delete(criteria)` (bulk, no prior SELECT — same distinction as TypeORM's
`Repository.update()`/`.delete()` vs. `.save()`/`.remove()`), and `create_query_builder(alias)`.

### Application-assigned keys: `insert()`

`save()` picks INSERT or UPDATE from the primary key, so an entity whose key you assign yourself
(a UUID, a natural key) cannot be inserted through it — it would issue an UPDATE that matches
nothing. Use `insert()` (on `Repository` and `EntityManager`), which always issues an INSERT and
still stamps `CreateDateColumn`/`UpdateDateColumn`:

```python
await self.repository.insert(Invoice(id=str(uuid.uuid4()), number="INV-1", tenant_id=tenant_id))
```

A duplicate key raises the driver's integrity error. It is the only write an `append_only` entity
with a pre-set key will accept.

### Mixins

`@Entity()` also collects `Column()`/relation markers from plain (non-entity) base classes, so a
mixin can contribute columns to every entity that inherits it — `austial.tenancy.Tenanted` is one.
Attributes declared on the entity class itself win over the mixin's; mixin columns are appended after
the class's own and are regular constructor fields.

`FindOptions` supports `where` (a dict is one AND-of-equality group, a `list[dict]` is
OR-of-AND-groups), `relations` (single-level eager-loading via `LEFT JOIN`), `order_by`, `skip`,
`take`.

A `where` value can be wrapped in `In`/`NotIn` (mirrors TypeORM's `In()`) for membership tests
instead of equality:

```python
from austial.orm import In, NotIn

pending = await repository.find(FindOptions(where={"status": In(["PENDING", "MANUAL_REVIEW"])}))
active = await repository.find(FindOptions(where={"status": NotIn(["REJECTED"])}))
```

`IsNull()` and `NotNull()` compile to `IS NULL` / `IS NOT NULL`. A plain `None` value is `= NULL`, which
never matches, so use these to filter on an unset nullable column — and to claim a row atomically, for
example consuming a single-use token with `update({"token_hash": h, "used_at": IsNull()}, {"used_at": now})`
and checking `affected == 1`:

```python
from austial.orm import IsNull

unused = await repository.find(FindOptions(where={"used_at": IsNull()}))
```

Comparing a native Postgres `ENUM` column this way (equality or `In`/`NotIn`) "just works" without
any `CAST` — `EntityManager` resolves the column's real enum type from schema metadata and binds
the parameter with it, so no app-code workaround is needed here.

### Append-only entities

Pass `append_only=True` to `@Entity()` for rows that must only ever be inserted, never mutated or
removed — audit logs, ledger entries, anything with a regulatory retention requirement:

```python
from austial.orm import Column, Entity, PrimaryGeneratedColumn


@Entity(append_only=True)
class LedgerEntry:
    id: int = PrimaryGeneratedColumn()
    description: str = Column()
    amount: int = Column()
```

Composes with the optional table-name positional, e.g. `@Entity("ledger_entry",
append_only=True)`.

This is enforced at the `EntityManager` level — the single choke point every `Repository` method
funnels through — not by convention in your service code:

- `repository.insert(entity)` works for any key (including an application-assigned one);
  `repository.save(entity)` still works for the INSERT path (primary key unset); calling it again
  on an already-persisted instance (primary key set, which `save()` would otherwise treat as a
  full-column UPDATE) raises.
- `repository.update(criteria, partial)`, `repository.remove(entity)`, and
  `repository.delete(criteria)` always raise, unconditionally — there's no legitimate partial
  update or delete path for an append-only entity.

All four raise `austial.orm.AppendOnlyViolationError` (a subclass of `OrmError`), naming the
entity and the attempted operation.

**What this guard does *not* cover:** it's an application-level check inside `EntityManager`,
not a database-level trigger, `REVOKE`, or row-level-security policy — raw SQL run outside the
ORM (a migration, a `psql` session, a DB role with direct table access) is not stopped by this.
Pair it with an actual DB-level guard (e.g. a `REVOKE UPDATE, DELETE` grant or a trigger) if you
need enforcement that survives someone bypassing the ORM entirely.

### Aggregation

Alongside `count(options)`, `Repository[T]` has `sum(column, criteria=None, group_by=None)` and
the lower-level `aggregate(fn, column, criteria=None, group_by=None)` (`fn` is
`"SUM" | "AVG" | "MIN" | "MAX"`) for numeric rollups — e.g. total AUM across matching holdings:

```python
total_aum: float = await holdings_repository.sum("quantity", criteria={"status": "ACTIVE"})
```

Pass `group_by` (a sequence of attribute names) to get a breakdown instead of a single scalar —
e.g. AUM per currency:

```python
by_currency: list[dict] = await holdings_repository.sum("quantity", group_by=["currency"])
# [{"currency": "USD", "value": 125000.0}, {"currency": "EUR", "value": 42000.0}]
```

Without `group_by`, `sum`/`aggregate` return a single `float` (`0.0`, not `None`, when no rows
match — SQL's `SUM` of zero rows is `NULL`, normalized here). With `group_by`, they return one
`dict` per group actually present in the data (the group-by attribute names as keys, plus
`"value"`) — groups with no matching rows don't appear, standard SQL `GROUP BY` semantics. Same
scope as `count()`: WHERE (+ here, `GROUP BY`) only, no joins/paging, single-level (no dotted
relation paths) group-by columns.

## Relations

```python
from austial.orm import Column, Entity, JoinColumn, ManyToOne, OneToMany, PrimaryGeneratedColumn


@Entity()
class Owner:
    id: int = PrimaryGeneratedColumn()
    name: str = Column()
    cats: list["Cat"] = OneToMany(lambda: Cat, inverse_side="owner")


@Entity()
class Cat:
    id: int = PrimaryGeneratedColumn()
    name: str = Column()
    owner: Owner = ManyToOne(lambda: Owner, join_column=JoinColumn(name="owner_id"))
```

`OneToOne`, `OneToMany`, `ManyToOne`, `ManyToMany` all work the same way TypeORM's do, with one
deliberate deviation: TypeORM stacks `@JoinColumn()`/`@JoinTable()` decorators above the relation
decorator, but Python's "marker as default value" trick only allows one right-hand side per
attribute — so `JoinColumn`/`JoinTable` are passed as a `join_column=`/`join_table=` kwarg
instead. The target entity accepts either the class directly or a zero-arg callable (`lambda:
Cat`) for forward references.

Eager-load a relation with `FindOptions.relations` or `QueryBuilder.left_join_and_select()`:

```python
owners = await owner_repository.find(FindOptions(relations=["cats"]))
```

## `QueryBuilder`

For anything `FindOptions` can't express, drop to the fluent query builder — mirrors TypeORM's
own `createQueryBuilder()`:

```python
cats = await (
    repository.create_query_builder("cat")
    .left_join_and_select("cat.owner", "owner")
    .where("cat.age > :age", {"age": 2})
    .and_where("owner.name = :name", {"name": "Alice"})
    .order_by("cat.name", "ASC")
    .take(10)
    .get_many()
)
```

WHERE clauses are always a raw SQL fragment plus a **separate** bound-params dict — values are
never string-formatted into the SQL text, only ever bound through the DBAPI driver. This is what
makes `.where()`/`.and_where()`/`.or_where()` (and everything built on top of them, including
`FindOptions.where`) SQL-injection-safe by construction.

For the common cases of equality and membership, `.where_eq()`/`.and_where_eq()`/`.or_where_eq()`
and `.where_in()`/`.and_where_in()`/`.or_where_in()` (plus `.where_not_in()` and its `and_`/`or_`
variants) generate the bind params for you — no need to invent placeholder names:

```python
qb.and_where_eq("cat.name", "Tom").and_where_in("cat.age", [2, 3, 4])
```

Pass `cast_text=True` when the target column is a native Postgres `ENUM` (or any column where a
string-typed bind param needs it) — it wraps the column reference in `CAST(<column> AS TEXT)`,
ANSI SQL so it also works against the SQLite driver used in tests:

```python
qb.and_where_eq("s.status", "MANUAL_REVIEW", cast_text=True)
qb.and_where_not_in("s.status", ["VERIFIED", "REJECTED"], cast_text=True)
```

`QueryBuilder` deals with arbitrary joined aliases, so unlike `FindOptions.where`'s `In`/`NotIn`
(which resolves the real column type automatically), this is an explicit opt-in rather than
auto-detected.

**Reserved-word table/column names:** a table or column name that collides with a SQL reserved
keyword (`user`, `order`, `group`, `check`, ... — `user` is reserved in Postgres, for example) is
safe everywhere the framework builds a query *for* you — `FindOptions.where`, the
bare-scalar-primary-key shorthand (`repository.update(id, {...})`/`.delete(id)`),
`find_one_by`/`find_by`, and `FindOptions.order_by` all quote table/column identifiers
automatically. Raw fragments you write yourself via
`.where()`/`.and_where()`/`.or_where()`/`.order_by()`/`.add_order_by()` on `QueryBuilder` are
**not** auto-quoted — same contract as TypeORM's own querybuilder — so quote them yourself (e.g.
`.where('"order".total > :n', {"n": 2})`) if your alias or column is a reserved word.

## Transactions

```python
async def transfer_cat(data_source: DataSource, cat_id: int, new_owner_id: int) -> None:
    async def _run(manager: EntityManager) -> None:
        cat = await manager.find_one_by(Cat, {"id": cat_id})
        cat.owner_id = new_owner_id
        await manager.save(cat)

    await data_source.transaction(_run)
```

`DataSource.transaction(callback)` opens one connection, binds a fresh `EntityManager` to it, and
runs `callback` — commits on clean return, rolls back automatically if `callback` raises.

## Migrations with Alembic

`austial.orm` doesn't ship its own migration runner — use [Alembic](https://alembic.sqlalchemy.org)
directly. `DataSource.get_metadata()` returns the `sqlalchemy.MetaData` describing every entity the
`DataSource` was constructed with, which is what Alembic's `env.py` needs as `target_metadata`:

```python
# migrations/env.py
from src.app_module import entities  # whatever list you pass OrmModule.for_root(entities=...)
from austial.orm import DataSource, SQLiteDriver

data_source = DataSource(SQLiteDriver("sqlite+aiosqlite:///./austial.db"), entities)
target_metadata = data_source.get_metadata()
```

Building the entity catalog only walks entity/relation metadata — it opens no DB connection, so
this is safe to call before `DataSource.initialize()` too, which matters for Alembic: its process
must not open the app's real connection pool just to import `target_metadata` at module load time.

This is the one deliberate exception to `austial.orm`'s "SQLAlchemy stays hidden behind `Driver`"
rule — Alembic's own API requires a real `sqlalchemy.MetaData` instance, so `get_metadata()` is the
single documented seam where that type crosses the public API boundary.

## Swapping in a different database

Nothing above the `Driver` interface (`Repository`, `EntityManager`, `QueryBuilder`,
`DataSource`, every decorator) is dialect-specific — pick `type_="postgres"` or `type_="sqlite"`
in `OrmModule.for_root()`/`for_root_async()` and everything else keeps working unchanged. See
[Health Checks](/techniques/health-checks) for how `DatabaseHealthIndicator` uses the same
`DataSource` to verify connectivity via `data_source.driver.execute_raw("SELECT 1")`.
